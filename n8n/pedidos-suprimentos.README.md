# Ingestão n8n — Pedidos (aba Suprimentos)

Workflow: `pedidos-suprimentos.workflow.json`. Alimenta a tabela
`pedidos_suprimentos` (Supabase, projeto `gebjlhkywtnpfqjrakok`, o mesmo já
usado pelo dashboard-main e pelo painel-mse).

## Antes de importar — não confundir com a tabela `suprimentos` existente

A tabela `suprimentos` que já existe hoje (usada pelo `dashboard-main`) é
uma lista **curada manualmente** pelo planejamento (item, escopo, prazo
limite, prioridade, observações de diligenciamento) — **não** vem dessa
API. `pedidos_usuarios_api` é dado **bruto do ERP** (pedido de compra,
fornecedor, valor, itens, datas de entrega) — outra fonte, outro grão,
tabela nova (`pedidos_suprimentos`), sem relação de schema com a antiga.
As duas podem coexistir; decidir qual alimenta a tela nova do painel-mse é
decisão de produto separada desta ingestão.

## SQL da tabela (rodar no SQL Editor do Supabase)

```sql
create table public.pedidos_suprimentos (
  id bigint generated by default as identity primary key,
  id_obra bigint not null,
  obra_nome text,
  banco_s1 text not null,
  numero_pedido text not null,
  numero_requisicao text,
  tipo_descricao text,
  status_pedido text,
  solicitante text,
  comprador text,
  fornecedor text,
  fornecedor_cnpj text,
  valor numeric,
  valor_liquido numeric,
  desconto jsonb,
  acrescimo numeric,
  frete jsonb,
  data_pedido date,
  data_entrega date,
  entrega_atualizada date,
  descricao text,
  grupo text,
  observacoes text,
  itens jsonb not null default '[]'::jsonb,
  raw jsonb,
  criado_em timestamptz not null default now(),
  atualizado_em timestamptz not null default now(),
  constraint pedidos_suprimentos_banco_numero_key unique (banco_s1, numero_pedido)
);

create index pedidos_suprimentos_id_obra_idx on public.pedidos_suprimentos (id_obra);
create index pedidos_suprimentos_datas_idx on public.pedidos_suprimentos (data_entrega, entrega_atualizada);

comment on table public.pedidos_suprimentos is
  'Pedidos de compra por obra, via API do PortalMSE (pedidos_usuarios_api). 1 linha por pedido (chave natural banco_s1+numero_pedido) -- NAO confundir com a tabela suprimentos (lista curada manualmente pelo planejamento, fonte e grão diferentes).';

alter table public.pedidos_suprimentos enable row level security;

create policy "leitura anon pedidos_suprimentos"
  on public.pedidos_suprimentos
  for select
  to anon, authenticated
  using (true);

create policy "service_role tem acesso total"
  on public.pedidos_suprimentos
  for all
  to service_role
  using (true)
  with check (true);
```

**Suposição a confirmar com dado real**: a chave única é `(banco_s1,
numero_pedido)` — a doc da API não afirma isso explicitamente, é a melhor
suposição a partir dos campos documentados (não há um `id` numérico único
na resposta). Se o primeiro `upsert` falhar por violação de unicidade
inesperada (dois pedidos "iguais" que na verdade são diferentes), essa
chave precisa ser revista — sinal de alerta a observar na 1ª carga real.

## Passo a passo

1. **Rodar o SQL acima** no Supabase (SQL Editor) antes de qualquer coisa.
2. **Importar o workflow** no n8n: Workflows → Import from File →
   `pedidos-suprimentos.workflow.json`.
3. **Criar a credencial da API do PortalMSE** (nó "Buscar pedidos por
   obra"):
   - Tipo: **Bearer Token** (`httpBearerAuth`)
   - Nome: `PortalMSE - Pedidos (Suprimentos)` (nome exato esperado pelo
     workflow)
   - Token: os 64 caracteres fornecidos pela equipe MSE. **Nunca cole o
     token em chat/documento** — cadastre direto no formulário de
     credencial do n8n.
4. **Credencial do Supabase**: se você já configurou o fluxo de Orçamentos
   Complementares antes, a credencial `Supabase - API Portal
   (service_role)` já existe e este workflow reaproveita ela — não precisa
   recriar. Se for a 1ª vez, ver o `README.md` do fluxo de Orçamentos
   Complementares (mesma pasta) pro passo a passo dessa credencial.
5. **Rodar manualmente uma vez** ("Execute Workflow") antes de ativar o
   agendamento — confira quantos pedidos vieram por obra
   (`select id_obra, count(*) from pedidos_suprimentos group by id_obra`)
   e se bate com uma expectativa razoável.
6. **Ativar** o workflow (agendado pra 07:00, ajustável no nó "Agendamento
   Diário" — 06:00 já está ocupado pelo fluxo de Orçamentos
   Complementares).

## Decisões de desenho, pra quem for mexer depois

- **6 obras fixas na lista** (`Lista de obras`), sem CNPEM - Auditório (id
  103) de propósito — decisão já tomada de que essa obra não faz parte do
  painel. Diferente do fluxo de OCs, aqui NÃO dá pra descobrir as obras a
  partir dos dados (a API exige `obra_id` por chamada, sem "lista todas as
  obras"), então a lista fixa é praticamente inevitável — se uma obra nova
  entrar no painel, tem que lembrar de adicionar aqui também.
- **`?all=true` por obra, não globalmente** — a doc avisa que `all=true`
  sem filtro pode travar (36 mil registros de todas as empresas); por obra
  o volume deve ser bem menor. Se na prática uma obra tiver volume alto
  demais e o `all=true` travar mesmo assim, trocar por paginação manual
  (`per_page=200` + loop de `page`) nessa obra.
- **Upsert em LOTE por obra** (1 POST com array de N pedidos), não 1 POST
  por pedido — bem mais rápido que uma chamada por linha. Risco conhecido:
  se uma obra tiver volume muito grande, o corpo da requisição pode
  esbarrar em limite de tamanho do PostgREST/Supabase — se acontecer,
  quebrar em lotes menores (ex. 500 linhas por POST) é o próximo passo.
- **Modo do Code node "Montar linhas por obra" é "Run Once for All
  Items"** (o padrão, não mudar) — diferente do bug do fluxo de Orçamentos
  Complementares (onde o modo certo era "Each Item"), aqui o certo É o
  padrão, porque a transformação é 1 obra → N pedidos (fan-out), não 1 → 1.
- **Pareamento obra↔resposta HTTP por posição** (mesma ordem de
  entrada/saída) com guard explícito (erro se as contagens não baterem) —
  evita silenciosamente juntar pedido de uma obra com o id de outra se
  algum dia esse pressuposto de ordem deixar de valer.

## Consumo no painel (ainda não implementado)

```
GET {SUPABASE_URL}/rest/v1/pedidos_suprimentos?id_obra=eq.{obraId}&select=*&order=data_entrega.asc
```

A regra de "crítico" (atrasado / vence hoje / no prazo) mencionada em
[[02 - Escopo e Telas]] como pendência do setor Suprimentos **não foi
definida nem implementada aqui** — isso é decisão de produto (quais
status_pedido contam, se `entrega_atualizada` sempre tem prioridade sobre
`data_entrega`, etc.), fora do escopo desta tarefa de ingestão.
