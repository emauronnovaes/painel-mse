# Ingestão n8n — Mapa de Compras (aba Suprimentos)

Workflow: `mapa-compras-suprimentos.workflow.json`. Alimenta a tabela
`itens_mapa_compras` (Supabase, projeto `gebjlhkywtnpfqjrakok`, o mesmo já
usado pelo dashboard-main e pelo painel-mse).

Fonte: `mapa_compras_api` do PortalMSE — guia em
`https://portalmse.com.br/microservices/mapa_compras_api/GUIA_USUARIO.php`.

## Antes de importar — o que a doc da API NÃO diz (leia isto primeiro)

O guia da API é bem mais magro que os das 2 integrações anteriores (OC e
Pedidos): não tem nenhum exemplo de JSON de resposta completo pra
`/v1/itens` nem `/v1/requisicoes`, só uma tabela com nome/tipo/descrição
de cada campo. Isso deixou 3 pontos em aberto, todos já cobertos com
defesa no código pra não gravar lixo silenciosamente, mas que precisam de
confirmação na 1ª execução real:

1. **Formato do envelope da resposta** — não confirmado se é
   `{ "data": [...] }`, um array direto, ou outra chave (`items`,
   `results`). O Code node `Montar linhas por obra` tenta `data` primeiro
   (é o formato da API irmã `pedidos_usuarios_api`), cai pra array direto,
   e **lança erro explícito** se nenhum dos dois bater — não existe
   caminho onde ele grava 0 linhas sem avisar.
2. **Nomes exatos dos campos `melhor_oferta_*`** — a doc só diz "melhor
   oferta unitário/subtotal/fornecedor" em texto corrido, sem nomear os
   campos JSON de verdade. Usei `melhor_oferta_unitario`,
   `melhor_oferta_subtotal`, `melhor_oferta_fornecedor` como palpite mais
   provável. Se vierem `null` na 1ª carga real, o item inteiro continua
   disponível em `raw` (jsonb) — é só olhar lá pra achar o nome certo e
   ajustar o Code node.
3. **Tabela `requisicoes_mapa_compras` (cabeçalho do RMI) NÃO foi criada
   ainda.** A doc não detalha nenhum campo de `/v1/requisicoes` além de
   confirmar que `mapa_id` corresponde ao campo `id` desse endpoint — não
   dá pra desenhar uma tabela sem saber as colunas de verdade (seria
   fabricar dado, o que este projeto trata como erro grave). Por ora,
   `itens_mapa_compras` guarda `requisicao` (número RMI) e
   `id_mapa_compras` (id interno) em cada item, o que já é suficiente pra
   agrupar/filtrar por requisição na tela. Se precisar de campo que só
   existe no cabeçalho (status da RMI, data de abertura, aprovador etc.),
   me passe uma resposta real de `/v1/requisicoes?obra_id=X&per_page=2` e
   eu desenho a 2ª tabela.

**Sobre a chave da API**: nunca cole ela em chat/documento — igual às 2
integrações anteriores, cadastre direto no formulário de credencial do
n8n (passo 3 abaixo).

**Rate/volume**: a doc cita 28.563 requisições no total (todas as ~20
obras da MSE), maior obra com 10.881 — mas nenhuma das 6 obras do
painel-mse é citada como a maior, então o volume por obra aqui deve ser
bem menor. Segue o mesmo padrão do fluxo de Pedidos: `all=true` **por
obra**, não globalmente (a doc avisa que sem filtro pode travar). Se
alguma obra tiver volume grande demais e travar mesmo assim, trocar por
paginação manual (`per_page=50` + loop de página) nessa obra.

## SQL da tabela (rodar no SQL Editor do Supabase)

```sql
create table public.itens_mapa_compras (
  id bigint generated by default as identity primary key,
  id_obra bigint not null,
  obra_nome text,
  id_mapa_compras bigint not null,
  requisicao text,
  codigo_seq text not null,
  descricao text,
  unidade text,
  quantidade numeric,
  preco_referencia_bd_s1 numeric,
  subtotal_referencia_bd_s1 numeric,
  custo_meta_orcamento numeric,
  subtotal_custo_meta_orcamento numeric,
  saldo_orcamentario numeric,
  saldo_quantidade numeric,
  quantidade_pedida numeric,
  total_consumido numeric,
  tem_pedido boolean,
  fornecedor_ref text,
  projeto_ref text,
  melhor_oferta_unitario numeric,
  melhor_oferta_subtotal numeric,
  melhor_oferta_fornecedor text,
  raw jsonb,
  criado_em timestamptz not null default now(),
  atualizado_em timestamptz not null default now(),
  constraint itens_mapa_compras_chave_key unique (id_obra, id_mapa_compras, codigo_seq)
);

create index itens_mapa_compras_id_obra_idx on public.itens_mapa_compras (id_obra);
create index itens_mapa_compras_id_mapa_compras_idx on public.itens_mapa_compras (id_mapa_compras);
create index itens_mapa_compras_tem_pedido_idx on public.itens_mapa_compras (tem_pedido);

comment on table public.itens_mapa_compras is
  'Itens de requisicoes/mapas de compra por obra, via API do PortalMSE (mapa_compras_api). 1 linha por item (chave natural id_obra+id_mapa_compras+codigo_seq). Nomes exatos de melhor_oferta_* nao confirmados pela doc da API -- ver raw se vierem nulos. Tabela de requisicoes (cabecalho do RMI) NAO foi criada ainda: a doc nao detalha os campos de /v1/requisicoes.';

alter table public.itens_mapa_compras enable row level security;

create policy "leitura anon itens_mapa_compras"
  on public.itens_mapa_compras
  for select
  to anon, authenticated
  using (true);

create policy "service_role tem acesso total"
  on public.itens_mapa_compras
  for all
  to service_role
  using (true)
  with check (true);
```

**Suposição a confirmar com dado real**: a chave única é `(id_obra,
id_mapa_compras, codigo_seq)` — `codigo_seq` é descrito como "código
sequencial do item", então presumo que só é único DENTRO de uma
requisição (`id_mapa_compras`), não globalmente. Se a 1ª carga real
disparar erro de unicidade inesperado (dois itens "diferentes" com o
mesmo trio), essa chave precisa ser revista.

## Passo a passo

1. **Rodar o SQL acima** no Supabase (SQL Editor) antes de qualquer coisa.
2. **Importar o workflow** no n8n: Workflows → Import from File →
   `mapa-compras-suprimentos.workflow.json`.
3. **Criar a credencial da API do PortalMSE** (nó "Buscar itens por
   obra"):
   - Tipo: **Bearer Token** (`httpBearerAuth`)
   - Nome: `PortalMSE - Mapa de Compras (Suprimentos)` (nome exato
     esperado pelo workflow)
   - Token: a chave fornecida pela equipe MSE para essa API. **Nunca cole
     o token em chat/documento** — cadastre direto no formulário de
     credencial do n8n.
4. **Credencial do Supabase**: se você já configurou algum dos 2 fluxos
   anteriores (Orçamentos Complementares ou Pedidos), a credencial
   `Supabase - API Portal (service_role)` já existe e este workflow
   reaproveita ela — não precisa recriar. Se for a 1ª vez, ver o
   `README.md` do fluxo de Orçamentos Complementares (mesma pasta) pro
   passo a passo dessa credencial.
5. **Rodar manualmente uma vez** ("Execute Workflow") antes de ativar o
   agendamento. Nessa 1ª execução, o objetivo principal é validar os 3
   pontos em aberto da seção acima:
   - Se o node "Montar linhas por obra" lançar erro de "formato de
     resposta inesperado", abrir a saída do node "Buscar itens por obra"
     pra ver a forma real do JSON e ajustar a linha `const itens = ...`.
   - Depois de gravar, checar no SQL Editor:
     `select id_mapa_compras, codigo_seq, melhor_oferta_unitario, melhor_oferta_subtotal, melhor_oferta_fornecedor, raw from itens_mapa_compras limit 5;`
     — se as 3 colunas `melhor_oferta_*` vierem todas `null` mas `raw`
     tiver alguma chave parecida (`melhor_oferta`, `oferta_unitaria`
     etc.), é sinal de nome errado — ajustar o Code node.
   - Conferir quantidade de linhas por obra:
     `select id_obra, count(*) from itens_mapa_compras group by id_obra;`
     e comparar com uma expectativa razoável (a doc não dá volume por
     obra, então isso é só um sanity check, não uma validação exata).
6. **Ativar** o workflow (agendado pra 07:30 — 06:00 já é o fluxo de
   Orçamentos Complementares, 07:00 é o fluxo de Pedidos).

## Decisões de desenho, pra quem for mexer depois

- **6 obras fixas na lista** (`Lista de obras`), sem CNPEM - Auditório
  (id 103), mesmo padrão do fluxo de Pedidos — essa API também exige
  `obra_id` por chamada, sem "lista todas as obras".
- **`?all=true` por obra, não globalmente** — mesmo raciocínio do fluxo
  de Pedidos (a doc avisa que `all=true` sem filtro em obra grande pode
  travar).
- **Upsert em LOTE por obra** (1 POST com array de N itens), não 1 POST
  por item — mesmo padrão dos 2 fluxos anteriores.
- **Conversão numérica explícita no Code node** (`num()`) em vez de
  confiar que a API sempre manda número de verdade — a API irmã
  (`pedidos_usuarios_api`) já mandou valor monetário como string mesmo a
  doc dizendo "número" (`valor_final` etc., ver
  `orcamentos-complementares.README.md`). Programar defensivamente aqui
  evita o mesmo problema silencioso se `mapa_compras_api` fizer o mesmo.
- **Modo do Code node "Montar linhas por obra" é "Run Once for All
  Items"** (o padrão, não mudar) — mesmo motivo do fluxo de Pedidos: a
  transformação é 1 obra → N itens (fan-out), não 1 → 1.
- **Pareamento obra↔resposta HTTP por posição**, com guard explícito —
  mesma proteção dos outros 2 fluxos.
- **`raw jsonb` guarda o item inteiro** — rede de segurança pros 3 pontos
  em aberto da seção "Antes de importar": nada se perde mesmo se
  `melhor_oferta_*` vier com nome errado ou se um campo novo aparecer que
  ninguém documentou.

O setor "Suprimentos" (`suprimentos-criticos`) continua placeholder — ver

GET {SUPABASE_URL}/rest/v1/itens_mapa_compras?id_obra=eq.{obraId}&select=*&order=requisicao.asc,codigo_seq.asc

A regra de "crítico" (prazo × impacto, mencionada em
[[02 - Escopo e Telas]] como pendência do setor Suprimentos) **não foi
definida nem implementada aqui** — essa API nem tem campo de prazo/data
por item (diferente de `pedidos_suprimentos`, que tem `data_entrega`),
então a régua de "crítico" provavelmente vai precisar CRUZAR as duas
tabelas (`itens_mapa_compras` pelo lado do orçamento/saldo,
`pedidos_suprimentos` pelo lado do prazo de entrega) — decisão de produto
separada desta ingestão.
